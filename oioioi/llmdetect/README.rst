Detection of solutions generated by LLMs, for the staff of a contest.

The module orders participants by how much their submissions look pasted
from an LLM chat and shows why, so that the staff knows whom to talk with.
It never disqualifies anybody: a high score is a hypothesis to check by
asking the participant to explain their code. Disqualifications still go
through ``oioioi.disqualification``.

It works from the first submission of a camp, on a CPU, without training
data and without sending participants' code anywhere.

Setup
-----

1. Add ``'oioioi.llmdetect'`` to ``INSTALLED_APPS`` and migrate.
2. Optionally, add ``'oioioi.llmdetect.middleware.ProblemViewMiddleware'``
   to ``MIDDLEWARE`` (after ``CurrentContestMiddleware``), so that the time
   from opening a statement to submitting is known. Without it, time is
   counted from the start of the round.
3. Before each round, add LLM solutions of its problems on the *LLM
   references* page (contest admin menu, *LLM detection*), or import them
   with ``manage.py llmdetect_import_references CONTEST DIR``, where
   ``DIR/<problem short name>/<model>__<prompt>__<n>.cpp`` are the files.
   Generate tens per problem with the models participants really use and
   prompts that imitate a participant ("short, no comments, like a
   high-school student", a sample of their code as the style to copy,
   fixing a wrong solution). Keep wrong solutions too.
4. Mark the rounds written under supervision, if there are any, as
   *supervised rounds* in the settings. Their submissions anchor each
   participant's style with triple weight.

The panel is for contest admins only (not basic admins). After the camp,
``manage.py llmdetect_purge CONTEST`` deletes the data, keeping anonymized
decisions for calibration.

Generating references
---------------------

The *LLM references* page can ask LLMs for solutions: pick a problem,
*Load statement* (text extracted from its PDF/HTML/zip statement), check
and edit the text, choose models, prompt styles (plain, in Polish, like a
high-school student, like an olympiad competitor, disguised) and how many
solutions each. Exactly the text in the box, with a one-line instruction,
is sent; participants' code never is. Jobs run in the background, in the
``llmdetect-generator`` supervisor program (``manage.py
llmdetect_generator``; ``--once`` stops when nothing can be done now). Each
answer's longest code block becomes a reference.

The generator makes one request at a time, to whichever provider may be
asked now, so the free limits of all configured providers add up. Each
provider can have ``min_interval`` (seconds between requests),
``daily_limit`` (requests per quota day) and ``reset_utc_hour`` (when its
quota day starts). A provider answering 429 waits for the time it gives
(``Retry-After`` and rate-limit reset headers), or with growing pauses and,
after a few in a row, until its daily reset; its jobs stay queued and go on
by themselves. The page shows each provider's requests today and when it
can be asked next. ``manage.py llmdetect_models [provider] [--free]``
lists the models each provider offers.

Without any provider, or for chats without an API, the *Copy* buttons put
the exact prompt (instruction and statement) on the clipboard to paste into
a chat; the answer is then added under *Add by hand*.

Models are configured in ``LLMDETECT_PROVIDERS`` (an example is in the
settings template). Two kinds of providers:

* ``"type": "openai"``: any OpenAI-compatible chat completions API, given
  ``base_url``, ``api_key`` and ``models``. That covers free tiers
  (OpenRouter's ``:free`` models, Google Gemini, Groq, Mistral), paid APIs
  (OpenAI, DeepSeek, paid tiers of the same) and a model on your own
  machine (Ollama, vLLM, llama.cpp server). ``min_interval`` spaces the
  requests to stay within free-tier limits; 429 answers are retried.
* ``"type": "anthropic"``: Claude through the official ``anthropic`` SDK;
  declined requests fall back server-side to another Claude model.

Free tiers have low daily limits and may use what is sent to train models
(Google states this for the free Gemini API tier). Statements of a camp
are secret until it starts, so for unpublished problems use paid tiers
that do not train on your data, or a local model. Consumer chat apps
(the free ChatGPT, Claude or Gemini websites) have no API and cannot be
used; their answers can still be pasted on the page by hand.

How it works
------------

Features of each submission are computed once: pasted code at submission
time (only then is it known that it was pasted), uploaded files after
judging, in the evaluation worker. Risks are recomputed for the whole
contest when the panel is opened and something changed (seconds at camp
scale), or with ``manage.py llmdetect_update CONTEST``.

Two representations of the code (``features.py``):

* a *style vector* of ~35 stylometric features: comments (full English
  sentences are typical of LLMs, rare in olympiad code), identifiers,
  idioms (``std::`` vs ``using namespace std``, macros, ``bits/stdc++.h``,
  debug output, commented-out code), layout;
* *winnowing fingerprints* (as in MOSS) of the token stream with
  identifiers, numbers and strings replaced, so renaming variables,
  deleting comments and reformatting do not hide copied code.

Signals (``scoring.py``), each in [0, 1] with an explanation:

=================  =========================================================
Close to LLM       Fingerprints shared with the nearest reference, above what
                   participants usually share with them on that problem.
LLM-like style     Style typical of LLM code, regardless of the author.
Style shift        Far from the author's own style *and* closer to LLM code.
Unlike own style   Far from own style only (weak; maybe copied from a peer).
Unusually fast     First good submission much sooner than other participants.
Much code at once  Many new lines per minute since the previous version.
Rewritten          A failed version replaced by unrelated code.
First try          Full score at once on a problem few solved (weak).
Above own level    Solved a hard problem while weak on the others.
Pasted             Pasted, while the participant usually uploads files.
Like a peer        Shares much code with another participant.
Chat leftovers     ```, "Here is", "Time complexity", "Step 1:"... in the code.
Web characters     No-break and zero-width spaces, typographic quotes...
Broken habits      Habits the participant keeps, changed (see below).
Unfamiliar names   Few identifiers the participant has used before.
=================  =========================================================

*Habits* (``habits.py``) are things a person writes the same way every
time: the template before the first function, the set of macros,
``bits/stdc++.h`` or separate headers, ``using namespace std`` or ``std::``,
the ``long long`` alias, the exact fast IO line, global arrays or local
vectors, how the size constant is written, the ``main`` signature, a
``solve()``/test loop, line endings (uploaded files only: pasted code
always arrives with CRLF), indentation, braces and ``else``, spacing after
``if``, around operators and after commas, naming style and function
names. A habit counts when it is kept in at least 80% of at least 3 other
submissions of the participant. A break weighs more when participants
rarely break that habit, more when it goes the LLM way (e.g. to
``cin.tie(nullptr)``), and is ignored when many participants break it on
the same problem (the problem forces it). The participant page shows the
habits of a submission next to the usual ones.

The *profile* of a participant is the weighted mean and variance of their
style vectors on other problems, shrunk towards the population (a prior
worth 5 submissions), with older submissions weighing less (0.9 per day).
Submissions that already look like LLM code do not enter the profile, so
somebody who uses an LLM from the first day cannot make it look normal;
the absolute style signal still catches them. Deviations are compared
with how much other participants deviate on the same problem.

The risk is ``sigmoid(-3 + sum(weight * signal))``; signals only raise
it. Weights are in ``scoring.DEFAULT_WEIGHTS`` and can be overridden with
``LLMDETECT_WEIGHTS`` in settings. Participants are ordered by the sum of
the risks of their three worst problems. Decisions of the staff are stored
with the signals at that time, to refit the weights once there are enough
of them; a confirmed submission becomes a reference for its problem.

Submissions sent after the end of their round (camps allow solving
problems again after they are discussed) get only the signals that look at
the code itself: references and style.

Limits
------

It does not detect using an LLM for the idea when the participant writes
the code, nor LLM code retyped by hand. The weights are set by hand, not
fitted on data yet. The style vector can be replaced with a trained
encoder of authorship style by changing ``features.style_vector``.
