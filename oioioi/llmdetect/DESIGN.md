what is tied to SIO2 and has to be replaced when porting.

## 1. Goal and principles

The module orders the participants of a programming contest (an olympiad
training camp) by how likely it is that some of their submissions were
written by an LLM rather than by themselves, and explains why. The staff then
talk to the most suspicious participants.

Principles that shaped every decision:

- **A score is a reason to talk, never a proof.** Every signal is shown with
  the facts behind it ("88% of the code matches an LLM reference; others
  usually 20%"), so the staff can judge it.
- **Compare a person with themselves first.** Olympiad participants have
  strong, stable habits (`bits/stdc++.h`, `#define ll long long`, fast IO
  lines, global arrays). A sudden change towards what LLMs write is the
  strongest behavioural signal. Comparing with other participants comes
  second, and always relative to how others behave *on the same problem*,
  because problems force code shapes.
- **Additive, explainable model.** Each signal is a number in [0, 1] with a
  weight; the risk is a logistic function of their weighted sum. No black box,
  every contribution is visible.
- **No participant code leaves the server.** The server never calls an LLM.
  LLM reference solutions are generated by the staff on their own machines,
  from problem statements only, and pasted in.
- **Robust to hostile code.** Participants control the input; everything is
  bounded in time and size (section 12).

## 2. Overview of the pipeline

```
 submission sent ──► Stage 1: analyse the code (once, cached)
                       lexer → stylometric features → LLM-style score
                             → winnowing fingerprints, line hashes
                             → habits, chat leftovers, pasted characters

 staff opens the panel (or a cron job) ──► Stage 2: assess the whole contest
   all submissions of participants + references + statement views
        + earlier contests (profiles only) + staff decisions
   ├─ independent signals: LLM reference, LLM style, chat leftovers, pasted chars
   ├─ per participant profile (weighted, shrunk to the population)
   │    → deviation, style shift, broken habits, unfamiliar names
   ├─ behaviour: bursts, rewrites, pasting
   ├─ scores: fast solve, above own level, first try
   └─ similarity to other participants
   → risk per submission → score per participant → review queue
```

Stage 1 depends only on the code. Stage 2 is recomputed for the whole contest
at once (seconds for hundreds of participants and thousands of submissions),
which keeps the results consistent when rounds, scores, references or
decisions change.

## 3. Data model

What the algorithm needs, independent of SIO2:

| Entity | Fields used |
|---|---|
| **Submission** | id, user, problem (and the problem's identity across contests), contest, round, date, score and max score, source code, file name, whether it was *pasted* into a web form |
| **Round** | start and end date, *supervised* flag (written without internet) |
| **Statement view** | user, problem, the first time they opened the statement |
| **LLM reference** | problem, code, model label, prompt label, kind (*generated* by the staff / *confirmed* case), its features and fingerprints |
| **Decision** | contest, user, optional submission, verdict (*no concerns* / *to talk with* / *confirmed*), note, reviewer, date, the risk and signals at that moment |
| **Config per contest** | supervised rounds, earlier contests and their weight, state of the last computation (time, newest submission included, dirty flag, read errors) |
| **Stored per submission (stage 1)** | version, language, pasted, paste_known, features, fingerprints, line hashes, number of code lines, habits, time computed |
| **Stored per submission (stage 2)** | risk, signals `{name: {value, contribution, detail}}`, context (profile, nearest reference, most similar peer, habits table, ...) |

Only submissions of **participants** are assessed: staff (anyone with a
permission in the contest, and superusers) are left out. Submission kinds
`NORMAL` and `IGNORED` count; others (e.g. test runs) do not.

## 4. Stage 1: analysis of one piece of code

### 4.1 Language and lexer

The language family comes from the file extension: `c cc cpp cxx h hpp java`
→ C family (also the default), `py` → Python, `pas` → Pascal.

A small hand-written lexer splits the code into tokens `(kind, text)` with
kind `id`, `num`, `str`, `op` or `pp` (a whole preprocessor line, with `\`
continuations), and collects comment texts separately (`//`, `/* */`; `#` and
docstrings in Python; `{ }` and `(* *)` in Pascal). Multi-character operators
(`<<=`, `->`, `::`, `&&`, ...) are single tokens.

### 4.2 Stylometric features

34 numbers describing *how* the code is written, not what it does. Ratios are
in [0, 1]; counts are per 100 non-blank lines.

| Group | Feature | Meaning |
|---|---|---|
| Comments | `comment_ratio` | comments per non-blank line (max 1) |
| | `prose_comment_ratio` | share of comments that are prose: ≥3 words, letters ≥60% of the text, no code inside |
| | `sentence_comment_ratio` | share of comments that are sentences: prose, ≥4 words, starting with a capital |
| | `english_comment_ratio` | share of words in prose comments that are common English code words ("the", "compute", "initialize", "edges", ...) |
| | `commented_code_ratio` | share of comments containing code (`;` at the end, `cout`, `for (`, a call, an assignment) |
| | `comment_words_per_100` | words in comments |
| Identifiers | `ident_mean_length` | mean length of identifier uses (keywords and library names excluded) |
| | `long_ident_ratio` | share of distinct identifiers with ≥6 characters |
| | `multiword_ident_ratio` | share in camelCase or snake_case |
| | `short_ident_ratio` | share with ≤2 characters |
| | `upper_ident_ratio` | share in UPPER case (longer than 1) |
| Idioms | `std_qualified_per_100` | `std::` prefixes (`std::vector`; not the `std` of `using namespace std`) |
| | `using_namespace_std` | 0/1 |
| | `bits_header` | 0/1 `bits/stdc++.h` |
| | `includes_per_100`, `defines_per_100` | `#include`, `#define` lines |
| | `type_aliases_per_100` | `typedef` and `using X =` |
| | `fast_io` | 0/1 `sync_with_stdio` |
| | `debug_traces_per_100` | `cerr`, `DEBUG` or `#ifdef` lines |
| | `return_zero` | 0/1 `return 0; }` at the very end |
| | `endl_ratio` | `endl` / (`endl` + `\n`) |
| | `printf_ratio` | (`printf`+`scanf`) / (those + `cout`+`cin`) |
| | `const_per_100`, `auto_per_100` | `const`/`constexpr`, `auto` |
| | `long_long_spelled_per_100` | `long long` written out |
| | `reference_params_per_100` | `const T&` parameters |
| Layout | `brace_own_line_ratio` | share of lines with `{` that are just `{` |
| | `tab_indent_ratio` | share of indented lines indented with a tab |
| | `indent_unit` | most common indentation unit (8, 4, 3, 2 or 1 spaces) |
| | `blank_line_ratio` | blank lines / all lines |
| | `mean_line_length` | mean length of non-blank lines |
| | `spaced_operator_ratio` | binary operators with spaces on both sides |
| | `multi_statement_line_ratio` | lines (not `for`) with more than one `;` |
| | `trailing_space_ratio` | lines ending with whitespace |

**Style vector.** The same 34 features in this order, with counts per 100
lines, `ident_mean_length`, `mean_line_length` and `indent_unit` replaced by
`log(1 + x)`, so a few extra comments in a short program do not dominate.

### 4.3 LLM-style score

A hand-set logistic score of how typical the features are of LLM-written
competitive code. Each feature is divided by a cap and clipped to [0, 1]:

```
llm_style = sigmoid(-2.0 + Σ weight · clip(feature / cap, 0, 1))
```

| Weight | Feature | Cap |
|---:|---|---:|
| +1.6 | sentence_comment_ratio | 0.5 |
| +1.0 | english_comment_ratio | 0.4 |
| +0.8 | comment_words_per_100 | 60 |
| +1.0 | multiword_ident_ratio | 0.4 |
| +0.6 | long_ident_ratio | 0.5 |
| +0.8 | std_qualified_per_100 | 10 |
| +0.5 | reference_params_per_100 | 3 |
| +0.4 | const_per_100 | 6 |
| +0.3 | return_zero | 1 |
| +0.3 | spaced_operator_ratio | 1 |
| −0.8 | using_namespace_std | 1 |
| −0.8 | bits_header | 1 |
| −0.8 | defines_per_100 | 4 |
| −0.6 | type_aliases_per_100 | 3 |
| −1.0 | debug_traces_per_100 | 2 |
| −1.0 | commented_code_ratio | 0.3 |
| −0.8 | short_ident_ratio | 0.8 |
| −0.6 | multi_statement_line_ratio | 0.2 |

The explanation gives the score and both sides: up to three features that
make the code look like LLM code and up to three that make it look unlike it
("LLM-likeness 5%. Like LLM code: return 0 at the end. Unlike LLM code: using
namespace std, one- or two-letter identifiers"), so a low score is not
explained by its few LLM-like features alone.

### 4.4 Fingerprints (similarity of code)

Winnowing (Schleimer, Wilkerson, Aiken 2003, as in MOSS), which survives
renaming, changing constants, removing comments and reformatting:

1. **Normalize** the token stream: drop preprocessor lines; identifiers become
   `I` unless they are keywords or *library names* (`vector`, `push_back`,
   `sort`, `cin`, `priority_queue`, ... — kept because they carry how the
   solution is built and nobody renames them); numbers → `N`; strings → `S`.
2. **k-grams** of k = 12 tokens, each hashed with CRC32.
3. **Winnowing** with a window of 6 hashes: from every window keep the
   minimum; the fingerprints are the distinct kept hashes.
4. **Cap**: keep the 4000 *smallest* hashes. As in MinHash, every document then
   keeps the same part of the hash space, so containment between capped sets
   stays meaningful.

Similarity is **containment**: `containment(A, B) = |A ∩ B| / |A|`, the share
of A's fingerprints that occur in B (asymmetric: a short program fully
contained in a long one scores 1).

### 4.5 Line hashes and code lines

- **Line hashes**: CRC32 of every non-blank line with all whitespace removed
  (at most 5000). Used to count how many lines a version adds to the previous
  one (multiset difference).
- **Code lines**: non-blank lines that are not `#include`, `#define`, `using`,
  `import` or `from` lines.

### 4.6 Habits

Things a person writes the same way every time. Each habit is a short value,
mostly the idiom itself, so a change can be shown as it is. `None` means the
habit does not apply (e.g. no fast IO line). C-family only, except
`line_endings`, `indent` and `naming`.

| Habit | Possible values (examples) | Typical of LLMs |
|---|---|---|
| `includes` | `bits/stdc++.h`, `separate` | `separate` |
| `namespace` | `using namespace std;`, `std::` | `std::` |
| `ll_alias` | `#define int long long`, `#define ll long long`, `typedef long long ll;`, `using ll = long long;`, `none` (only when 64-bit ints are used) | `none` |
| `fast_io` | the exact line, e.g. `ios_base::sync_with_stdio(0); cin.tie(0)` | `ios::sync_with_stdio(false); cin.tie(nullptr)` (and `std::` version) |
| `storage` | `global arrays`, `vectors` | `vectors` |
| `size_constant` | shape of the array size constant: `N = 1eX+c`, `MAXN = digits`, `UPPER = 1eX`, ... | — |
| `main` | `int main()`, `signed main()`, `int main(void)`, `int main(argc, argv)` | `int main()` |
| `test_loop` | `solve() in a test loop`, `solve()`, `test loop in main`, `plain` | `plain` |
| `line_endings` | `CRLF`, `LF` (only for uploaded files, see 4.8) | — |
| `indent` | `tabs`, `4 spaces`, `2 spaces`, ... (≥3 indented lines) | `4 spaces` |
| `braces` | `own line`, `same line`, `mixed` (≥3 opening braces; ≥70% decides) | `same line` |
| `else` | `} else {`, `}\nelse`, `mixed` | `} else {` |
| `keyword_space` | `if (`, `if(`, `mixed` | `if (` |
| `operator_space` | `spaced`, `tight`, `mixed` | `spaced` |
| `comma_space` | `, `, `,`, `mixed` | `, ` |
| `naming` | `camelCase`, `snake_case` (≥25% of names ≥3 chars), `short names` (≥50% ≤2 chars), `plain words` | `camelCase`, `snake_case` |
| `function_names` | `descriptive` (multi-word or mean ≥9 chars), `short` (mean ≤5), `words` | `descriptive` |

Besides the categorical habits:

- **template**: the lines before the first function definition, with
  whitespace normalized (at most 60 lines of 200 characters) — the personal
  "header" most competitors paste into every solution;
- **macros**: names of `#define`d macros (at most 100);
- **identifiers**: the distinct names the author chose (keywords, library and
  standard names excluded; at most 400 of 64 characters);
- **chat leftovers** (searched in comments; the code fence anywhere):

  | Name | Pattern | Strength |
  |---|---|---:|
  | markdown fence | ```` ``` ```` | 1.0 |
  | here is | "here is", "here's" | 0.9 |
  | explanation | "Explanation:" | 0.9 |
  | complexity | "time/space complexity" | 0.8 |
  | example usage | "example usage" | 0.8 |
  | approach | "Approach:", "Intuition:" | 0.8 |
  | big O | `O(n log n)` and similar | 0.5 |
  | step N | "Step 1:" | 0.5 |
  | markdown | `**bold**`, `` `code` `` | 0.4 |
  | edge case | "edge case(s)" | 0.4 |

- **pasted characters** (characters a web page or chat interface leaves in
  copied text; a byte order mark at the very start is ignored):

  | Characters | Strength |
  |---|---:|
  | no-break, narrow no-break, figure space; zero-width space, (non-)joiner, word joiner, zero-width no-break space | 0.9 |
  | other invisible format characters (Unicode `Cf`) | 0.7 |
  | em dash, arrow `→`, `≤`, `≥` | 0.4 |
  | typographic quotes, en dash | 0.3 |

### 4.7 Pasted or uploaded

A submission is **pasted** when its code was typed or pasted into the web
form instead of uploaded as a file. This is only known when the submission is
created. The module records it then; SIO2 also marks it by the stored file
name `__pasted_code.*`.

### 4.8 Line endings, and when paste is unknown

Code sent through a browser form always arrives with CRLF line endings, so
line endings only say something about **uploaded** files (an editor setting
that rarely changes). For submissions analysed *after the fact* (an older
contest, analysed when the panel is first opened) it is unknown whether they
were pasted: they get `paste_known = false`, and `line_endings` is left out of
their habits. Otherwise a participant who sometimes pastes and sometimes
uploads would get a false broken habit.

## 5. Stage 2: assessing a contest

### 5.1 Inputs

- All submissions of participants of the contest (staff excluded), sorted by
  date, with their stage 1 analysis (computed now if missing; failures are
  counted and the first error is shown on the panel).
- Supervised rounds, LLM references of the contest's problems, statement
  views, confirmed decisions.
- Optionally **earlier contests** (section 5.5).

Each submission becomes an *item* with: style vector, LLM-style score and
reasons, fingerprints, habits, supervised flag, score fraction, and:

- **during round**: sent between the start and the end of its round (or the
  round has no end). After a round its problems are discussed and solved
  again, so similarity, speed and solving above one's level mean nothing then;
  those signals only apply during the round.
- **score fraction**: points / max points, clipped to [0, 1]; without a
  maximum, points / 100.
- **start time**: when the participant could start working on the problem:
  the round start, or the first time they opened the statement if later.

### 5.2 Boilerplate

Per problem, a fingerprint present in submissions of **more than 40%** of the
participants of that problem (when there are at least 5) is boilerplate
(input reading, fast IO, the obvious loop) and is removed before comparing
code. If fewer than 5 fingerprints remain, all are kept.

### 5.3 Profiles: the participant's own style

A profile describes how a participant normally writes. To judge item *i*, it
is built from the participant's **other** submissions *o*, each with a weight:

```
w(i, o) = 0                                   if o is on the same problem as i
                                              (same problem in another contest too)
                                              or o was confirmed as LLM-written
w(i, o) = gate(o) · history_weight            if o is from an earlier contest
w(i, o) = gate(o) · trusted(o) · 0.9^days     otherwise

gate(o)    = clip((0.8 − independent(o)) / 0.5, 0, 1)
trusted(o) = 3 if o is from a supervised round, else 1
days       = |date(i) − date(o)| in days (submissions after i count too)
```

`independent(o)` is the largest of o's signals that need no profile (LLM
reference similarity, LLM style, chat leftovers / pasted characters). The
**gate** stops code that already looks LLM-written from defining what the
author's style is (a "poisoned" profile): at 0.3 or less it counts fully, at
0.8 or more not at all.

**Pool bounds**: for each problem only the latest 3 submissions of the
participant are used (many submissions to one problem add little, and without
a bound the cost grows with the square of a participant's submissions). From
earlier contests, the same per problem, and then only the latest 40.

### 5.4 Shrinkage

A profile built from little data is unreliable, so it is pulled towards the
population (all submissions of the contest), as if κ = 5 average submissions
were added:

```
population mean μ_j and variance σ²_j of each style feature j (variance ≥ 0.02)
W        = Σ w(i, o)                        (profile weight)
mean_j   = (Σ w·x_oj + κ·μ_j) / (W + κ)
var_j    = max(0.02, (Σ w·(x_oj − mean_j)² + κ·σ²_j) / (W + κ))
style_p  = (Σ w·llm_style(o) + κ·mean llm_style) / (W + κ)
confidence = W / (W + κ)
```

With 3 earlier submissions at weight 0.5, W = 1.5 and confidence 23%; the
panel marks profiles under 25% as uncertain.

### 5.5 Earlier contests

The staff can choose earlier contests (e.g. previous camps). Submissions of
the **same participants** there are added to the pools with
`history_weight` (0.5 by default, 0.05–1), with no decay in time, as described
in 5.3. They are analysed once (stage 1) and cached, but **never scored** and
never compared with other participants. Confirmed decisions of those contests
also exclude submissions from profiles. Only contests the admin fully
administers can be chosen, since profiles show code.

### 5.6 Robust z-scores

Many signals compare a value with the same value of other participants on the
same problem, using median and MAD so that a few cheaters do not move the
baseline:

```
z(v) = (v − median) / (1.4826 · MAD)      (standard deviation if MAD ≈ 0; 0 if fewer than 3 values)
```

## 6. The signals

Each signal is a value in [0, 1] plus the facts behind it. *(r)* marks signals
that only apply to submissions sent during their round.

### Code compared with LLMs

**`llm_reference`** — close to an LLM solution of the same problem.
```
sim       = max over references r of containment(specific(item), specific(r))
baseline  = median over participants of their best sim on this problem (0 if < 5 participants)
threshold = max(0.35, baseline + 0.15)
value     = clip((sim − threshold) / max(0.9 − threshold, 0.05), 0, 1)
```
Solutions of one problem share code anyway, so this is relative to how close
participants usually get. `specific` = fingerprints without boilerplate.

**`llm_style`** — the LLM-style score of 4.3, as it is.

**`chat_leftovers`** — `1 − Π(1 − strength)` over the leftovers found (4.6).

**`paste_characters`** — the same over the pasted characters found.

### Code compared with the author

**`deviation`** and **`style_shift`** — far from the author's own style.
```
d    = mean over features j of (x_j − mean_j)² / var_j        (distance from the profile)
z    = robust z of d among submissions of the same problem (all submissions if < 5)
dev  = clip((z − 1) / 3, 0, 1)
deviation   = dev · confidence
toward      = clip((llm_style − style_p) / 0.4, 0, 1)
closeness   = max(toward, llm_reference value)
style_shift = dev · closeness · confidence
```
Some problems force unusual code, hence the comparison with how far others
strayed from their own style on the same problem. `style_shift` is the
important one: unlike yourself **and** towards LLMs.

**`habit_break`** — broken habits. For each item, with a history of at least 3
weighted submissions:

- A categorical habit counts if its most common (weighted) value holds in
  **≥80%** of at least 3 submissions where it applies, and is not `mixed`.
  It is *broken* when the current value differs (and is not `mixed`).
- The **template** (≥3 usual lines) and **macros** (≥2 usual names): the usual
  lines/names are those present in ≥60% of the weighted history; broken when
  less than half of them are kept.
- **Forced by the problem**: if on this problem at least 4 participants had the
  habit and ≥30% of them broke it, the break is ignored (e.g. the statement
  suggests a template).
- **Strength** of a break depends on how rarely participants break that habit
  in the whole contest:
  ```
  rate     = (breaks + 1) / (cases + 5)
  strength = clip(ln(1 / rate) / 3, 0, 1)
  strength = min(1, 1.3 · strength)  if the change is towards an LLM value (and always for template/macros)
             0.6 · strength          otherwise
  value    = 1 − Π(1 − 0.8 · strength) over the broken habits
  ```

**`vocabulary`** — unfamiliar names. With a history of ≥3 and ≥4 current names
(≥2 characters): `overlap` = share of current names the author used before.
Compared by robust z with others on the same problem (≥5, otherwise all
submissions; at least 3): `value = clip((−z − 1.5) / 2.5, 0, 1)`. Shows the
new names (`numVertices`, `adjacency`, ...).

### Behaviour

**`burst`** *(r)* — much new code at once. Compared with the participant's
previous submission to the same problem: new lines = multiset difference of
line hashes, time = since that submission; for the first submission, all code
lines since the start time. With ≥20 new lines:
`rate = lines / max(minutes, 0.5)`, `value = clip((rate − 4) / 8, 0, 1)`
(4 lines a minute is normal, 12 is not).

**`rewrite`** — rewritten from scratch after a failed attempt. Previous
submission to the problem not fully solved, both ≥15 code lines:
`sim = (containment(a, b) + containment(b, a)) / 2`,
`value = clip((0.25 − sim) / 0.25, 0, 1)`.

**`pasted`** — pasted although the participant usually uploads files. With ≥3
other submissions: `rate` = share of the others that were pasted; if below
0.3, `value = 1 − rate / 0.3`.

### Scores

Per problem: `solve_rate` = share of participants who tried it with a best
score ≥ 0.9.

**`fast_solve`** *(r)* — the first submission with ≥50% of the points, ≥15 code
lines, came much faster than others' (≥4 others):
`value = clip((0.5·median − minutes) / (0.5·median), 0, 1)` — half the median
time or less starts counting.

**`score_surprise`** *(r)* — the first submission with ≥50% of the points
scored ≥90% on a problem that fewer than half solved, by a participant who is
weak on the other problems (≥5 participants):
`strength` = percentile of the participant's total on the other problems;
`value = clip((1 − strength) · (1 − solve_rate) / 0.5, 0, 1)`.

**`first_try`** *(r)* — full score at the first submission on a problem that
fewer than 30% solved (≥5 tried): `value = 1 − solve_rate / 0.3`.

### Other participants

**`peer_similarity`** *(r, both submissions)* — the largest share of the item's
specific fingerprints found in one submission of another participant:
`value = clip((sim − 0.5) / 0.4, 0, 1)`. Not an LLM signal by itself, but two
participants pasting the same chat answer look like this.

## 7. Combining signals into a risk

```
risk = sigmoid(−3.0 + Σ weight_s · value_s)
```

| Signal | Weight |
|---|---:|
| llm_reference | 3.5 |
| chat_leftovers | 3.0 |
| style_shift | 2.5 |
| habit_break | 2.5 |
| paste_characters | 2.0 |
| llm_style | 1.5 |
| fast_solve | 1.2 |
| rewrite | 1.0 |
| score_surprise | 1.0 |
| vocabulary | 1.0 |
| burst | 0.8 |
| peer_similarity | 0.8 |
| deviation | 0.5 |
| pasted | 0.5 |
| first_try | 0.3 |

With no signals the risk is sigmoid(−3) ≈ 5%. A submission is **flagged** at
risk ≥ 0.5, i.e. when the weighted sum reaches 3 (e.g. a strong LLM reference
match alone, or a habit break plus LLM style). Signals can only raise the risk,
and each one's contribution is stored and shown. The weights are hand-set
(overridable by a setting) and meant to be refitted on the staff's decisions
(section 10).

## 8. Ranking participants

Per participant, the worst submission of each problem; the participant's
**score** is the sum of the risks of their **3 worst problems** (so one
borderline problem does not dominate, and several suspicious problems add up).
The queue is ordered by this score and shows the number of flagged
submissions, the worst problems with their risks, the three signals that
contributed most, the profile confidence and the latest decision.

The participant page shows, for the chosen submission: every signal with its
explanation, the style profile (weight, confidence, share from earlier
contests, usual LLM-likeness, features that differ most), the habits table
(usual value, its share, current value, broken / forced by the problem), the
most similar submission of another participant, a timeline (round start,
statement opened, every submission with its score and risk), the code next to
the nearest LLM reference and next to the participant's *usual own code* (a
supervised submission if any, otherwise the one closest to their profile, on
another problem).

## 9. LLM reference solutions

The strongest signal needs solutions written by LLMs for each problem,
collected **before** the round. The server never calls an LLM:

1. **Prompts.** For each problem, the statement text (from its PDF / HTML /
   zip / txt, editable by the staff) with one of five instructions, imitating
   how participants ask:
   - *plain*: "Solve this competitive programming problem in C++. Read the
     input from standard input and write the output to standard output."
   - *polish*: the same in Polish;
   - *student*: "...like a high-school student at an olympiad would: short, no
     comments, short variable names";
   - *olympiad*: "...the way an experienced olympiad competitor would:
     bits/stdc++.h, using namespace std, macros, fast IO, global arrays";
   - *disguised*: "...then make the code look hand-written: rename the
     variables, remove all comments and do not explain anything".
2. **Generating.** By hand (copy a prompt into any chat) or with a standalone
   script (`tools/llm_references.py`, Python standard library only) run by the
   staff with their own API keys. It reads a prompts file
   (`{"format": "llmdetect-prompts/1", "prompts": [{"problem", "prompt",
   "text"}]}`), asks any OpenAI-compatible API (free tiers of several
   providers) and Claude, round-robin within each provider's `min_interval`
   and `daily_limit`, backs off on HTTP 429, writes answers as they come and
   continues where it stopped when run again.
3. **Bulk format** to paste or upload many answers at once:
   ```
   ### reference problem=abc model="ChatGPT free" prompt=student
   <code, or a whole chat answer: only its longest ``` code block (C++ or untagged) is kept>
   ### reference problem=abc model=groq/llama prompt=plain
   ...
   ```
   Values with spaces are quoted; `problem` may be left out when a default is
   chosen; code already stored for the problem is skipped; at most 5000 per
   upload.

Generate tens of references per problem with the models participants really
use, and keep wrong solutions too: their mistakes are a strong fingerprint.

## 10. Staff decisions and feedback

A decision (*no concerns*, *to talk with*, *confirmed*) is recorded per
participant, optionally about one submission, with a note, the reviewer and
the risk and signals at that moment (for calibrating the weights later). A
**confirmed** decision about a submission:

- adds its code as a *confirmed* LLM reference of its problem, so others who
  pasted similar code are found;
- removes it from the participant's profile (also when the contest is used as
  an earlier contest later);
- marks the contest for recomputation.

Decisions do not change scores; a disqualification is a separate step (in
SIO2 its own module; the camp ranking then counts the problem as 0, or removes
the participant for a whole-contest disqualification).

## 11. When things are computed

- **Stage 1** runs when a pasted submission is created (the code is at hand
  and it is known to be pasted), and for uploaded files in the evaluation
  worker once the submission is judged, so the participant never waits.
  Failures are only logged. Anything missing is computed when the panel is
  opened (marked `paste_known = false`). A version number
  (`FEATURES_VERSION`, now 5) makes stored analyses recompute when the
  analysis changes (the panel then reassesses the contest by itself);
  references recompute the same way.
- **Stage 2** runs when the panel is opened and the contest is *dirty* or has
  submissions newer than the last computation; on **Recompute**; or from a
  command (`llmdetect_update CONTEST...`, e.g. from cron). Settings,
  references, decisions and rejudging mark the contest dirty.
- **Statement views** are recorded by a middleware (first view per user and
  problem).
- **After the camp**, `llmdetect_purge CONTEST` deletes the data and keeps the
  decisions anonymized (no participant, reviewer or note) for calibration.

## 12. Robustness against hostile input

Participants control the code, so:

- every regular expression runs in linear time (bounded repetitions, matches
  starting at word boundaries, possessive quantifiers); comments are looked at
  only up to 1000 characters;
- stored analysis is bounded: 4000 fingerprints, 5000 line hashes, 400
  identifiers, 60 template lines of 200 characters, 100 macros, names of 64
  characters;
- profile pools are bounded (3 per problem, 40 from earlier contests);
- statements read for prompts are bounded (50 MB), bulk uploads too (5000
  references);
- all code shown to the staff is escaped.

## 13. What is tied to SIO2

Pure and portable as they are: `features.py`, `habits.py` (no Django) and the
logic of `scoring.py`. To port the rest, replace:

| In SIO2 | Replace with |
|---|---|
| `ProgramSubmission`, `Round`, `ProblemInstance`, `Contest` (Django models) | your submission / round / problem / contest records (section 3) |
| reading code through Filetracker (`submission.source_file.read()`) | your storage |
| the controller hooks `create_submission` (pasted code) and `submission_judged` (uploaded files) | hooks in your submission flow, or a periodic job |
| pasted = file name `__pasted_code.*` | a flag set when code comes from a text field |
| staff = `ContestPermission` holders and superusers | your notion of staff |
| `ProblemViewMiddleware` (statement views) | a log of when each participant opened each problem |
| scores as `IntegerScore`, `max_score` | a number and its maximum |
| statements from SIO2 problem packages (`query_statement`) | statement text from wherever you keep it |
| Django views, templates, translations, admin permissions | your UI |
| disqualification module, camp ranking | your ranking |

## 14. Limitations and ideas

- **Weights are hand-set**, from what LLM chats produce for olympiad problems
  and from tests, not fitted on data. The decisions (with the risk and signals
  stored at decision time) are meant to refit them, e.g. a logistic
  regression on confirmed vs. no-concerns submissions.
- **Habits and style need history.** The first days of a camp have little; the
  earlier-contests option and supervised rounds help. Profiles are marked
  uncertain under 25% confidence.
- **References must exist and be relevant.** Without them only style and
  behaviour work. New models produce new styles; regenerate per camp.
- **Evasion**: asking the LLM to imitate the participant's own code (pasting
  an old solution as a style example) defeats style and habits; the
  reference, timing, score and behaviour signals remain. A *disguised* prompt
  is included for that reason.
- **C++ first.** Habits are C-family only; features and fingerprints work for
  Python and Pascal too.
- **Fairness.** A high score is a reason to talk with the participant
  ("explain this part"), never a proof; the analysis must be mentioned in the
  rules (GDPR: purpose and basis; for minors, their parents).
